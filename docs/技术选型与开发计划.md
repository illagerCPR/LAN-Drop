# LAN-Drop 技术选型与开发计划（v1.0）

> 状态：**选型已确认**，进入 P0 落地。决策记录见 §7。
> 本文所有环境结论均来自 2026-09-29 在本机（WSL2 Ubuntu 26.04）的实测，非推测。

---

## 1. 目标与范围

以局域网为唯一传输通道，替代已下线的 Edge Drop，提供「文字 / 链接 / 文件」跨设备互传 + 会话历史。

| 能力 | 说明 | 优先级 |
| --- | --- | --- |
| 文字/链接互发 | PC ↔ 手机，即时到达 | P1 |
| 文件互传 | 单文件、多选、大文件（GB 级）、断点续传 | P1 |
| 会话历史 | 时间线式聊天页，两端都可查、可搜 | P1 |
| 传输记录缓存 | 手机端本地库缓存会话与传输记录（离线可看） | P1 |
| 系统分享面板 | 手机任意 App「分享 → LAN-Drop」直发 PC | P2 |
| 后台接收 | PC 发文件时手机收到通知，无需先打开 App | P2 |
| 免登录、免联网 | 不依赖任何云服务与账号 | P1（硬约束） |
| 多设备 | 一台 PC 服务端 ↔ 多台手机 | P3 |

**明确不做**（至少首版）：跨公网中继、端到端加密群聊、音视频、剪贴板全自动同步。

### 2.4 Windows 入站放行（**已完成，含一次分析纠错**）

**现象**：WSL 的 `eth2` = `192.168.1.100`，Windows `WLAN` 适配器同为该 IP（镜像模式共享）；
Windows 侧访问 `localhost:8787` 可达，但访问 `192.168.1.100:8787` **超时**。
据此我最初判断「Hyper-V 防火墙 `DefaultInboundAction = Block` 是拦路原因，手机必然连不上」。

**纠错**（以服务端日志为准）——上述推断**错了**：

```
{"req":{"url":"/","host":"192.168.1.100:8787","remoteAddress":"192.168.1.101",...},"res":{"statusCode":200}}
```

`192.168.1.101` 是手机，请求全部 200。也就是说：

1. **手机一直能连通**，`DefaultInboundAction = Block` 并未阻断这条路径；
2. 「Windows 访问本机 LAN IP 超时」是**假阴性**——镜像模式下 Windows 连自己持有的那个 IP
   走的是本机回环捷径，根本到不了 WSL 的监听套接字。**这个探测不能用来判断手机是否可达**，
   唯一可信的判据是服务端日志里的 `remoteAddress`（或手机实际打开页面）；
3. 真正需要放行的是**常规 Windows 防火墙入站规则**：脚本执行后，`LAN-Drop (TCP/UDP)`
   两条 Inbound Allow 规则生效，手机访问稳定；
4. `New-NetFirewallHyperVRule` 那两条**没有创建成功**（Hyper-V 规则表为空），但**不影响功能**。
   推测是 `-RemoteAddresses 'LocalSubnet'` 关键字不被该 cmdlet 接受，需要写显式 CIDR。

**最终有效对策**：以管理员运行一次 `scripts/windows-allow-lan.ps1`，放行 TCP 8787 + UDP 8788，
来源限定本地子网。

> 📌 **留给后续排查的经验**：判断「手机能否访问 WSL 服务」时，不要用宿主机访问自身 LAN IP
> 来探测（镜像模式下必然假阴性）；应直接看服务端日志的 `remoteAddress`。

> 📌 **PowerShell 脚本必须存为 UTF-8 with BOM**：Windows PowerShell 5.1 对**无 BOM** 的 `.ps1`
> 按系统 ANSI 代码页（中文系统为 GBK）解码，脚本里的中文字符串会变乱码，其中某些字节恰好是
> 引号或反引号，**直接破坏语法**，报出「参数列表中缺少参数」「意外的标记 )」等与真实原因毫不
> 相干的错误。
>
> 实际发生过的两种应对，优劣如下：
>
> | 做法 | 结果 | 评价 |
> | --- | --- | --- |
> | 手工「另存为 ANSI」再执行 | 能跑通 | 有效但不可持续：每次改动都要重存；且 ANSI 依赖系统区域设置，同一文件在英文版 Windows 上会被当成 CP1252，同样乱码 |
> | **UTF-8 with BOM** | 能跑通 | ✅ 采用。PS 5.1 与 PS 7 均正确读取，git / 编辑器友好，且不受系统区域设置影响 |
>
> `scripts/windows-allow-lan.ps1` 已固定为带 BOM 保存，**请勿去掉 BOM，也不要再手工另存为 ANSI**。
> 自查命令（0 即通过）：
> `powershell -c "[void][System.Management.Automation.Language.Parser]::ParseFile('脚本路径',[ref]$null,[ref]$e); $e.Count"`

备选（同样需管理员）：改 NAT 模式 + `netsh portproxy`；或直接把服务端跑在 Windows 侧 node.exe 上。
**首选仍是镜像模式 + 放行规则**——它让 WSL 与手机处于同一广播域，发现与传输都最自然。

### 2.5 Android 工具链定版（**已构建成功**，非推测）

首轮按「AGP 8.13.2 + compileSdk 36」求稳的设想**被生态现实否决**，实测经过如下：

1. 首次构建失败于 `checkDebugAarMetadata`，27 条问题，涉及 `androidx.compose.*:1.12.1`、`androidx.core:core:1.19.1`，**甚至 `com.squareup.okhttp3:okhttp-android:5.5.0`** —— 全部要求 `AGP ≥ 9.1.0` 且 `compileSdk ≥ 37`。
   → 结论：**降级 Compose 也救不回来**，整个现代 AndroidX 生态已迁移到 AGP 9，AGP 8.x 路线不可行。
2. 第二个坑：`platforms;android-37` **在 SDK 仓库中不存在**。Android 平台已改为小版本命名：`android-37.0` / `android-37.1` / `android-37.2`（无裸 `37`）。
3. 第三个坑：AGP 9.4.1 的 POM 显示其运行时依赖 **`kotlin-gradle-plugin:2.2.10`** —— 即「内置 Kotlin」的编译器就是 **2.2.10**。若把 Compose / serialization 编译器插件设成 2.4.20，会与 AGP 拉入的 KGP 冲突。**编译器插件版本必须等于 AGP 内置 KGP 版本**。

**最终定版（已 `assembleDebug` 成功）：**

| 组件 | 版本 | 说明 |
| --- | --- | --- |
| AGP | **9.4.1** | 最新稳定版（2026-09-24 元数据）；9.5 尚为 alpha |
| Gradle | **9.7.1** | AGP 9.0 要求 ≥ 9.1.0；取 9.7.1（2026-08-19）稳妥 |
| Kotlin 编译器插件 | **2.2.10** | 必须等于 AGP 9.4.1 内置的 KGP 版本 |
| KSP | **2.3.12** | AGP 9 要求 ≥ 2.3.6；KSP 自 2.3.0 起与 Kotlin 版本解耦 |
| compileSdk / targetSdk | **37** | 平台包名为 `platforms;android-37.2` |
| minSdk | **33** | 按确认结论（Android 13+） |
| build-tools | 36.0.0（AGP 默认）/ 37.0.0 亦已安装 | |
| Compose BOM | 2026.09.00 | |
| Room | 2.8.5 | KSP 处理，schema 正常导出 |
| kotlinx-serialization-json | 1.9.0 | 需与 Kotlin 2.2 匹配，不能用 1.11.0 |
| OkHttp | 5.5.0 | 注意其 `okhttp-android` 组件同样要求 AGP 9.1+ |

**AGP 9 迁移要点（本项目已落地）：**
- **不再应用 `org.jetbrains.kotlin.android`** —— AGP 9 内置 Kotlin 已取代它，且它与新 DSL 不兼容。
- Compose 与 serialization 属于「Kotlin 编译器插件」，**仍需显式应用**（`org.jetbrains.kotlin.plugin.compose` / `.serialization`）。
- 无需设置 `kotlin.compilerOptions.jvmTarget`，它默认取 `android.compileOptions.targetCompatibility`。
- `android.useAndroidX` 在 AGP 9 已默认为 true。

> ⚠️ **Room 陷阱（本次实际踩到）**：`@Entity(indices = [Index(value = [...])])` 与 `@Query` 里写的是**列名**，不是 Kotlin 属性名。`createdAt` 经 `@ColumnInfo(name = "created_at")` 映射后，索引必须写 `created_at`，否则 KSP 报 `referenced in the index does not exist in the Entity`。

## 3. 技术选型

### 3.1 服务端（PC 侧）：**Node.js + TypeScript** ✅ 推荐

| 方案 | 优 | 劣 | 结论 |
| --- | --- | --- | --- |
| **Node.js + TS（Fastify + ws）** | 环境现成；服务端/前端/协议同一语言；`node:sqlite` 内置；流式处理 GB 级文件毫无压力；Windows/Linux 同一份代码 | 需 Node 运行时（可后续用 SEA/pkg 打成单文件 exe） | ✅ **采用** |
| Rust + axum | 单静态二进制、内存占用低 | 本机无工具链，需装 ~1 GB；迭代速度慢一半以上 | ❌ 暂不采用，分发阶段可回头评估 |
| Go + gin | 单二进制、交叉编译方便 | 本机无工具链；与前端的类型共享断裂 | ❌ |
| Python | 已装 | 打包分发差、高吞吐流式转发不如 Node 自然 | ❌ |

**理由核心**：这是**局域网内网工具**，瓶颈是磁盘与 WiFi，不是 CPU；语言性能差异在这个场景下不可观测。开发速度、跨平台一致性、以及「一份协议定义三端共用」的价值远大于运行时性能。

### 3.2 Android 客户端：**原生 Kotlin + Jetpack Compose** ✅ 推荐

这是本次选型最关键的分歧点，把账算清楚：

| 方案 | 后台接收通知 | 切后台大文件传输 | 系统分享面板 | 环境成本 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **原生 Kotlin/Compose** | ✅ 前台服务 + WS 长连接 | ✅ | ✅ | 需装 Android SDK（约 1.5–2 GB，镜像速度 2~3 MB/s，约 15 分钟） | ✅ **采用** |
| PWA（服务端托管） | ❌ 无 Web Push 则必须开着页面 | ❌ 浏览器切后台易被杀 | ❌ | 0 | 作为**兜底与 PC 端 UI**保留，不作为手机主入口 |
| Capacitor 壳 | 需自己写原生插件才行 | 需插件 | 需插件 | 仍要 Android SDK，多一层构建 | ❌ 两头不讨好 |
| Flutter | ✅ | ✅ | ✅ | 额外 1 GB+ Flutter SDK，且多一门 Dart | ❌ |

**结论：原生 Kotlin**。上面三项（后台通知、后台传输、分享面板）正是 Edge Drop 体验的骨架，PWA 补不齐；而环境成本在本机是可接受的（镜像快、磁盘够、JDK 已有）。

**Kotlin 技术栈**：
- UI：Jetpack Compose + Material 3
- 本地缓存：Room（`消息表` / `传输记录表` / `设备表`）
- 网络：OkHttp（含 WebSocket）+ kotlinx.serialization
- 异步：Coroutines + Flow
- 后台：Foreground Service（`dataSync` 类型）+ 常驻 WS + 通知
- 文件：SAF / MediaStore 写 `Downloads/LAN-Drop`，规避存储权限弹窗
- DI：**首版手写容器**（不引 Hilt），减少首次构建的 KSP/注解处理风险；稳定后再评估

- `minSdk 33`（Android 13，按你的实际机型定，可省掉大量旧版本兼容分支）、`targetSdk 36`
  - 说明：若日后要给 Android 12 及以下用，只需把 `minSdk` 降到 26，并补 `POST_NOTIFICATIONS` 旧路径与存储权限分支；现在不做，避免无谓复杂度。

### 3.3 PC 端 UI：**服务端托管的 Web UI** ✅ 推荐

PC 本身是服务端，浏览器打开 `http://localhost:8787` 即用，同一份前端也直接服务手机浏览器（兜底 + 快速验证）。

- 应用包名：`io.github.illagercpr.landrop`
- 框架：**React 18 + Vite + TypeScript**（已确认）／Svelte／轻量原生
- 样式：手写 CSS 变量 + 少量工具类，避免重依赖
- 托盘常驻应用已落地：Tauri 2.x 壳 + Node sidecar（P4-6，2026-09-30；便携包随之放弃；2026-10-01 补齐 Linux AppImage 构建）

### 3.4 协议设计：**控制面走 WS，数据面走 HTTP** ✅

| 通道 | 承载 | 理由 |
| --- | --- | --- |
| `WS /api/v1/ws` | 文字消息、事件通知、在线状态、进度广播、配对请求 | 双向低延迟；**绝不在此传文件字节** |
| `HTTP /api/v1/files/*` | 文件上传/下载字节流 | 天然支持 `Range` 断点续传、浏览器直下、内存零拷贝流式转发；避免与聊天消息互相队头阻塞 |

草案接口：

```
GET    /api/v1/info                      服务信息、协议版本、服务端名
POST   /api/v1/pair        {code}        配对码换 deviceId + deviceToken
GET    /api/v1/messages?since=<seq>&limit 增量拉取（断线重连补偿）
POST   /api/v1/messages    {kind,text}   发文字/链接
POST   /api/v1/uploads     {name,size,sha256?} 创建上传会话
PATCH  /api/v1/uploads/:id?offset=<n>    分片续传（body 为裸字节流）
POST   /api/v1/uploads/:id/complete      落盘、生成消息、广播
GET    /api/v1/files/:id?range=          下载，支持 Range
```

- 单调递增 `seq`（服务端权威），客户端以 `since=seq` 增量补齐 —— 聊天记录不丢不重。
- `packages/protocol` 作为**单一事实源**：TS 类型 + JSON Schema → 生成/校验 Kotlin 侧字段名，防止两端字段漂移。
- 大文件默认分片 4 MiB，支持并发分片与断点续传；服务端流式落盘，不整文件进内存。

### 3.5 发现与配对

| 手段 | 定位 |
| --- | --- |
| **二维码**（Web UI 展示，内容含 IP:端口 + 一次性配对 token） | ✅ 主路径，最可靠 |
| **手动输入 IP:端口** | ✅ 兜底 |
| **UDP 广播 beacon**（8788，自定义固定格式） | ✅ 便利发现，比 mDNS 稳 |
| mDNS / Android NsdManager | 可选，部分 ROM 与 AP 隔离下不稳，不作主路径 |

配对流程：二维码/配对码 → 换取长期 `deviceToken`（存 Android Keystore / EncryptedSharedPreferences）→ 之后免配对。

### 3.6 存储

| 位置 | 介质 | 内容 |
| --- | --- | --- |
| 服务端 | `node:sqlite` | 设备、消息、传输记录、上传会话 |
| 服务端 | 文件系统 | `<dataRoot>/files/YYYY/MM/<uuid>_<原名>`，sha256 去重，可配保留期 |
| 客户端 | Room(SQLite) | 会话、消息、传输记录（**离线可看**），本地已读位点 |

`dataRoot` 默认：Linux `~/.local/share/lan-drop`；Windows `%LOCALAPPDATA%\LAN-Drop`。

### 3.7 安全

- 默认**只接受 RFC1918 私有网段来源**，公网来源直接拒绝（防误暴露到公网）。
- 所有写操作需 `deviceToken`；配对码短时效、一次性。
- 传输：**HTTP + Token（已确认）**——家庭内网、风险可接受、实现简单。
  - 演进位（P4 可选，不阻塞主线）：自签 TLS + **SPKI 指纹固定**，二维码直接携带证书指纹，客户端固定校验、免装 CA。协议层预留 `tls` 能力位，届时无需改动接口形态。
- Android 侧需 `network_security_config` 允许明文（若走 HTTP）。
- **剪贴板**：Android 10+ 后台读剪贴板受限、13+ 读取会弹提示，**不做自动剪贴板同步**，只做「前台点按发送剪贴板」。

### 3.8 打包与分发

- 服务端：`node` 直接跑；后续用 Node SEA 打成单文件 exe / Linux 可执行，Windows 侧提供「开机自启」脚本（计划任务或 `nssm`）。
- Android：debug 直装（`adb install`）+ release APK 自签名（密钥库随仓库外保存，CI secret）。

#### P2 踩坑记录（都是真机跑出来才发现的）

1. **配对码字母表不是纯数字**。服务端 `PAIRING_ALPHABET = "ABCDEFGHJKMNPQRSTUVWXYZ23456789"`
   （刻意排除 0/O、1/I/L），而客户端一度把输入框设成 `KeyboardType.NumberPassword`——用户根本敲不出字母。
   现在用 ASCII 键盘 + 输入即转大写；提示文案也改成「6 位配对码」而非「6 位数字」。
2. **进程被系统杀掉后，传输记录会永远停在「进行中」**。界面上是一条永不结束的进度条，
   服务端还留着 open 会话和 `.part` 临时文件（要等 24h TTL 才回收，实测堆积过 1.5 GB）。
   修法：`TransferRepository.reconcileInterruptedTransfers()` 在 App 启动时把
   `queued/running` 统一标记为失败，并顺手 `DELETE /uploads/:id` 清掉服务端临时分片；
   下载方向则删掉 MediaStore 里那条 `IS_PENDING` 隐藏行（因此创建目标后要立刻把 URI 落库）。
   首版不做跨进程续传，所以是「标记失败让用户重发」；P3 做续传时这里改成「读回服务端进度并恢复」。
3. **服务端 `device.online` 广播先于 `hello` 到达**。客户端不能假设「第一条消息一定是 hello」，
   两件事都要能独立处理（hello 用于水位校准，presence 用于在线数）。
4. **「在线设备数」包含本机**。因此「PC 是否在线」只能由 `onlineCount >= 2` 推断，
   而不能靠监听 presence 事件累计——自己连上时只会收到自己那条 `device.online`。
5. **下载目录是 `Download/LAN-Drop`**（MediaStore 的 `RELATIVE_PATH`，注意大小写与连字符）。
   验收时我用 `LanDrop` 去 `ls` 找不到文件，白排查了一轮。
6. **不要在有键盘弹出时按固定坐标点输入栏**。键盘弹出后输入栏上移约 1000px，
   按旧坐标点击会落到键盘上；`InputKeyEvent.ESC` 也收不起 Compose 的软键盘。
   自动化点击前一律先 `uiautomator dump` 取当前坐标。
7. **链路速率要单独测，别把网络慢当成实现慢**。本次 `adb pull` 8 MB 用了 15 秒（0.5 MB/s），
   而 App 内下载 20 MB 跑到 ~375 KB/s——达到链路 75%，属正常开销。
8. **文档必须与实现一致**：README 架构图里一直画着 `UDP :8788 局域网发现广播`，但代码里从没有过这个模块。
   本次已从图中删除并挪到 P3 规划，避免「照着文档找功能却找不到」。

#### P3-1 踩坑记录

1. **服务端必须 `ftruncate`，否则续传静默写坏文件。** `appendStreamToFile` 用 `flags: "a"`（`O_APPEND`）追加，
   而请求中途断流时（客户端被杀、WiFi 掉线、服务端 abort）`pipeline` 抛错返回，
   **已落盘的字节留在文件里**，数据库 `received_bytes` 却停在这一片之前——两者一旦不一致，
   下次从权威 offset 续传就把新数据接在残字节后面。
   这次用**负向验证**确认了它：注释掉 `truncateTo` 后，「续传后收尾」立刻从通过变成 `422 sha256_mismatch`
   （残字节恰好 512 KiB）。修法是在 PATCH 里、追加之前 `truncateTo(tempPath, receivedBytes)`，
   代价是重传不到一个分片，换来铁律「追加开始时文件长度恒等于本次起始 offset」。
   冒烟用例为此专门写了个**裸 TCP 掐断**的辅助函数——`fetch` 会等整个 body，造不出这个场景。
2. **下载方向的截断是兜底，不是必需——别把两者混为一谈。** `"rw"` 打开的 fd 不是 `O_APPEND`，
   `Os.lseek` 定位到 offset 后是逐字节覆盖，服务端 `Range` 返回的也正是从该 offset 开始的字节，
   所以对齐本身就已正确。保留 `ftruncate` 是为了把不变量写成显式的，
   防住「服务端返回的字节比文件原有尾巴还短」这类将来可能出现的情形。
   一开始我在代码注释里把两侧写成同一个坑，是过度归因——两侧的实现机制不同，必须分开说。
3. **`Os.ftruncate`/`Os.lseek` 优于 `FileChannel`。** channel 的所有权归 `FileOutputStream`，
   两者生命周期纠缠，`close()` 路径容易把 fd 关两次；fd 号一旦被系统回收，
   第二次关掉的就是别人的 socket——这类 bug 极难复现与定位。
4. **SAF 的读权限必须显式持久化，否则重启后无法续传。**
   `takePersistableUriPermission(uri, FLAG_GRANT_READ_URI_PERMISSION)`：不加这一步，
   权限随进程消失，进程被杀后就算记着进度也打不开源文件。传完/取消时再 `release` 还回去。
5. **只有读权限的 URI 不能用 `"rw"` 探测长度。** 启动收尾时我一度用 `openFileDescriptor(uri, "rw")`
   判断源文件还在不在，会抛 `SecurityException` 被吞成 `-1`，于是把**完全可续传**的任务误判成「现场丢失」。
   上传源固定用 `"r"` 探测。
6. **`CancellationException` 分不清「暂停」与「取消」。** 两者在协程层面完全一样，
   只能靠发起时记下的意图（`intents: MutableMap<String, CancelIntent>`）来区分收尾方式：
   暂停要保住两端现场（服务端会话留 `open`、MediaStore 半成品留着），取消才清场。
7. **暂停后立刻点「继续」会静默没反应。** 上一轮协程还在 `NonCancellable` 收尾时，
   `jobs` 里仍占着这个 id，新的启动请求被「已在跑」挡掉。修法是让恢复协程先 `join()` 上一轮再开工。
8. **失败不该一律判死刑。** 网络抖动时如果直接标失败并 `DELETE` 服务端会话，
   几百 MB 的进度就白费了。现在的判据是「4xx（除 408/429）与权限失效 = 永久失败，其余 = 可恢复」，
   可恢复的落到「已暂停」并提示原因。
9. **下载结束时必须显式核对字节数。** 服务端截断连接时 `read()` 返回 `-1` 而不是抛错，
   不核对就会把半截文件当成功落盘、从 `IS_PENDING` 转正——用户拿到一个坏文件却毫无提示。
10. **不做自动续传是有意的。** App 启动时 WiFi 常常还没就绪，自动重试会把本来可恢复的任务
    直接烧成失败；用户也未必希望一开 App 就占满带宽。所以启动收尾只落到「已暂停」，等一次点击。
11. **测试辅助脚本的过滤逻辑也会骗人。** 我写的 `uiautomator` 筛选器在 `--all` 模式下
    把「可点击但无文案」的节点也跳过了（Compose 的按钮文案在子节点上、可点击性在父节点上），
    于是「一个可点击节点都没有」；差点据此判定 UI 坏了。真机自动化里，
    「没找到」和「不存在」必须分开确认。
12. **debug 构建的包名带 `.debug` 后缀。** `applicationIdSuffix = ".debug"` 使实际包名是
    `io.github.illagercpr.landrop.debug`；用 `applicationId` 去 `am start` / `run-as` 会报
    「Activity class does not exist」，很容易误判成「没装上」。
13. **固定坐标点击在时间线里必然失效。** 多一行提示文案整体就下移约 100 px，按旧坐标会点空。
    一律「先 dump 取当前坐标再点」。

Web 控制台标题这些「回答我在跟哪台机器说话」的位置上——「服务端」是实现术语泄漏到界面，
多台 PC 时还全都同名。现在默认取主机名（`os.hostname()`，可用 `LAN_DROP_SERVER_NAME` 覆盖），
本机实测手机标题显示为 `SW-ShittimLight`。同时发现 `ConnectionStore.updateServerName()`
**从来没有被调用过**（死代码），PC 改名后手机永远显示配对那天的旧名字；
现在每次回到前台会顺带核对一次。

#### P3-2 踩坑记录

1. **前台服务只跟着「有没有活在跑」，不做常驻接收。** 本应用的收文件是「对方发来消息 →
   用户点下载」，没有一个需要 7×24 运行的后台任务；常驻只会白耗电、白占 `dataSync` 配额，
   还在状态栏挂一条去不掉的通知。**代价要写明**：应用长时间停留在后台且没有传输时，
   进程可能被冻结或回收，新消息通知会延迟到下次打开应用（届时增量同步会把消息补齐）。
   要真正做到「随时可达」，得再做一个用户可开关的常驻模式，而不是默认常驻。
2. **服务自己订阅 Room，而不是让仓储往里推进度。** 服务与界面共用同一个 `AppContainer`，
   进度只有一个真相（数据库）；否则就要维护「服务眼中的传输状态」这第二份副本，
   而它恰恰是最难保持一致的东西。
3. **`startForeground` 必须在 5 秒内调用**，而那一刻还没从数据库读到进度——先挂占位通知
   （「正在准备传输…」），收集器拿到第一帧再换成真实进度。
4. **`FOREGROUND_SERVICE_IMMEDIATE` 不是可选项。** Android 12+ 会推迟新前台服务的通知
   约 10 秒才显示；对「点了发送什么都没发生」的观感来说，那 10 秒很致命。
5. **Android 15 起 `dataSync` 型前台服务有「24 小时内累计 6 小时」配额**，用尽时系统调用
   `onTimeout(startId, fgsType)` 而不是直接杀进程。必须在这里主动收尾：把传输落成「已暂停」
   （两端现场都还在，能续）并明确告知用户；否则用户视角就是「文件传到一半，通知没了，也没任何解释」。
6. **Android 12+ 限制后台启动前台服务。** 我们的调用点都在用户动作路径上（点发送/下载/通知按钮），
   属于豁免情形，但豁免清单随版本变化且抛的是 `IllegalStateException`——必须兜住：
   通知挂不上只是少了提示，不能让用户的发送直接失败。
7. **通知渠道的重要性一旦建立就只有用户能改**，应用再也调不回来。所以一开始就分三条
   （进度=低、结果=中、消息=中），而不是图省事合成一条：否则用户想静音进度、
   保留消息提醒时无路可走。
8. **「用户主动暂停」与「网络中断暂停」只能靠 `error` 是否为空区分。**
   主动暂停走的是 `setStateIfExists(..., PAUSED, null)`，中断路径会写上原因。
   通知层复用了这个既有约定：前者静默（用户自己按的），后者必须提醒（屏幕关着的人
   不会知道文件已经静悄悄地不传了）。这是**跨层复用了别的模块的约定**，
   已在代码注释里写明——将来若有人给主动暂停也填上 `error`，通知就会开始乱响。
9. **`uiautomator dump` 在通知栏有进度通知持续刷新时会失败**（`ERROR: could not get idle state.`）：
   SystemUI 一直进不了 idle。只能重试（本次第 20 次才成功）。
   更隐蔽的是第二层坑：**dump 失败时不会写文件**，如果脚本失败后照旧去 `cat` 远端那个文件，
   读到的就是**上一次的旧 dump**——我的辅助脚本一开始正是如此，界面坐标「看起来正常」，
   据此得出的结论却全是错的。现在脚本先删远端文件、失败即退出（返回码 2）。
10. **服务不导出，`adb shell` 也起不动它。** `am startservice` 报
    `Requires permission not exported from uid`——这既是想要的安全属性，
    也意味着通知按钮**只能靠真实点击验证**，不能用命令行代劳。
11. **通知按钮的坐标很近，绝不能盲点或估算。** 本次「暂停」在 `(178,967)`、「取消」在 `(311,967)`，
    同一行相隔 133 px；点错就是直接把几百 MB 的半成品删掉。必须 dump 到真实坐标再点。
12. **`PendingIntent` 的相等性不含 extra。** 它只按 requestCode 与 Intent 的「过滤等价」部分比较，
    extras 不参与——两条不同传输的按钮若用同一个 requestCode，会互相覆盖成同一个 PendingIntent。
   所以要把传输 ID 掺进 requestCode。

自动发现解决「手输 IP」和「服务端换 IP 找不回」两件事；自动接收解决「每个文件都要点一下下载」。

设计决策：

- **客户端广播提问、服务端单播应答**（探测文本 `LANDROP-DISCOVER-v1`，UDP 8788；
  应答 `{ service, v, id, name, port }`）。不用服务端定时广播：平时无噪声、手机按需触发、
  应答是单播所以 Android 不申请 `MulticastLock` 也收得到。
- **发现端口与 HTTP 端口解耦**（8788 vs 8787）：Windows 防火墙 TCP/UDP 规则各自独立，
  复用就得给 HTTP 端口再开 UDP，语义混乱。服务端可用 `LAN_DROP_DISCOVERY_PORT` /
  `LAN_DROP_DISCOVERY` 覆盖或关闭；UDP 绑定失败只降级不致命。
- **凭据失效是独立状态**（`SocketState.CREDENTIALS_INVALID`），与「重连中」分离：
  4401/401 后停止重连并给出「解除配对重新配对」的出路；找回扫描在凭据失效时跳过
  （服务端活着，扫了也是同址空转）。
- **自动接收默认关 + 开启时刻即基准点**：自动落盘 = 静默占用存储 + 自动写入未确认内容，
  两者都该由用户显式同意；没有基准点的话，开启后第一次全量同步会把服务端历史文件全拉下来。

#### P3-3 踩坑记录

1. **手机「连接断开，正在重连…」挂了半天，根因在服务端设备表不在手机。**
   网络路径（手机 → HTTP 200）、应用进程、重连逻辑逐一排查都正常，最后对服务端日志才发现
   `/api/v1/messages` 全是 401——上一轮会话清理测试数据时把手机的设备行误删了，之后 PC 侧
   测试脚本又自注册了一条新行。教训两条：清理必须点名「我创建的那些」，绝不整表清；
   应用侧对 401 必须有明确状态（本条催生了 CREDENTIALS_INVALID）。
2. **`/tmp/send-file.mjs` 这类 PC 侧测试脚本每次运行都自注册一台新设备**（`PC/linux`），
   用完不删就会在设备表里累积僵尸行，还会干扰「设备行为什么变了」的排查。要么复用固定凭据，
   要么用完即删。
3. **拉取应用 Room 库必须 db/-wal/-shm 三个文件分别导出**到同一目录再打开，WAL 才会重放；
   把三个文件拼接成一个流再查会报 `no such table`。
4. **WSL2 镜像模式能收到局域网 UDP 广播**（此前只验证过 TCP）。手机发 `255.255.255.255:8788`
   的广播报文可以到达 WSL 里绑 `0.0.0.0` 的 dgram socket，防火墙沿用 `windows-allow-lan.ps1`
   里预留的 UDP 规则即可——「广播到不了 WSL」的担忧实测不成立。
5. **`erasableSyntaxOnly` 连构造器参数属性也禁**（`constructor(private readonly x: T)`），
   字段要自己声明再赋值——和禁 enum/namespace 是同一条规则，第一次写新服务端类时又踩了一次。
6. **junit 的 `assertNotNull` 不做智能转换**，断言后仍要 `!!`（或改用 kotlin.test 的断言），
   和项目里既有测试保持同一风格。

#### P3-4 踩坑记录

1. **合成二维码按 1px/模块编码时任何二值化器都解不出来**。测试里用 zxing `QRCodeWriter`
   传 `width=0` 会生成 33×33（MARGIN 后）的图，每个模块只有 1 像素——用真实 jar 逐一试过

2. **`MultiFormatReader.decode()` 内部会 `setHints(null)` 重置 hints**——先 `decode` 再指望
   之前设的 `POSSIBLE_FORMATS` 生效是错的。要 `setHints` 后用 `decodeWithState`；
   只解 QR 时这个组合还能省掉全格式轮询。
3. **zxing 3.5.4 的 `PlanarYUVLuminanceSource` 构造器是 8 参**（多出 `reverseHorizontal`），
   少一个参数编译不过。本项目 Y 平面不做镜像（QR 解码对 90° 旋转天然不变），传 `false`。
4. **`ProcessCameraProvider.getInstance()` 返回的 `ListenableFuture` 桥接协程不必引 Guava**：
   手写 `suspendCancellableCoroutine` + 直接执行器 `addListener` 十几行就够；
   相机必须在 `finally` 里 `unbindAll()`（扫到退出 / 返回键 / 异常三条路都要松开相机）。

#### P4-1 踩坑记录

1. **ESM 产物里跑 CJS 依赖会启动即崩**：fastify/avvio/ws 内部 `require("node:events")`，
   esbuild 在 ESM 格式下没有 `require`，其 `__require` 兜底直接抛
   `Dynamic require of "node:events" is not supported`（`server/src/index.ts` 都还没执行到）。
   解法是在 banner 里 `createRequire(import.meta.url)` 把 `require` 放回模块作用域，
   且必须在 banner（早于 esbuild 的 `__require` 初始化）里定义。
2. **自包含检查不能用正则扫产物文本**：ajv 把 `require("ajv/dist/runtime/uri").default`
   当**字符串字面量**写进生成代码，文本扫描会报出一堆"未打包依赖"（其实都在产物里）。
   改用 esbuild metafile 的真实模块图后误报消失。另外 CJS 侧写的是裸内建名（`assert`），
   ESM 侧写 `node:assert`，判定要同时认两种。
3. **`.ps1` 丢了 BOM 只有 Windows 上才炸**：编辑一次文件就可能把 BOM 吞掉，而
   PowerShell 5.1 会按 GBK 解码中文并报出与真实原因无关的语法错。现在出包脚本遇到
   无 BOM 的 `.ps1` 直接拒绝出包，仓库里另有 `pnpm fix:ps1-bom` 一键补齐（`--check` 只查）。
4. **`[ordered]` 不能当参数类型**：写 `[ordered] $Values` 会让**整个脚本解析失败**
   （"ordered 属性只能…"），要用 `[System.Collections.IDictionary]`。这条是被
   `verify-package.mjs` 里的真实 PowerShell 解析器检查抓出来的——Linux 上完全看不出来。
5. **PowerShell 往管道写中文是 GBK**：WSL 侧按 UTF-8 解码会得到乱码，报错信息变得没法读；
   调用前先 `[Console]::OutputEncoding = [Text.Encoding]::UTF8`。
6. **`Start-Process`/`*>` 重定向不会创建目录**：日志目录不存在时启动命令立刻失败，
   现象是"服务端一行日志都没有"。数据目录要先 `New-Item -Force` 建好。
7. **打包脚本自己漏字段**：`buildStage()` 返回的 meta 少了 `node` 版本，Windows 组装时
   去拉 `vundefined` 的 node.exe，报 404。跨函数传递的构建元数据要一次读全、整体透传。

| 单文件分享（3 MB，`-d <content-uri> --grant-read-uri-permission`） | ✅ 服务端接收的 sha256、文件名与本地探针完全一致 |
| 一次分享两个文件（`ACTION_SEND_MULTIPLE` + `--esa`，2 MB + 1 MB） | ✅ 两条文件消息按序落库，sha256 各自相符 |
| 一个 intent 内含同一张照片的两种 URI 形态（`…/images/media/<id>` + `…/file/<id>`） | ✅ 修复前 2 条上传、修复后 **1 条**（见「同一张照片被传两遍」） |
| 真实相册分享单张照片（修复后端到端确认） | ✅ 只上传 1 条（`seq 87`，sha256 与报障那次完全一致） |
| 应用在前台时分享（`onNewIntent` 路径） | ✅ 系统提示 "intent has been delivered to currently running top-most instance"，文字进输入框 |
| 应用内「文件」多选（SAF `OpenMultipleDocuments`） | ✅ **按文件名驱动完成自动化 E2E**（此前「选择器不暴露文件名」的前提有误，见踩坑 12）：两个探针文件（1243 B / 5687 B）逐字节到达服务端，sha256 与源一致，全程零盲点 |

踩坑：

1. **`EXTRA_STREAM` 只有裸 `Uri` 时没有读授权**：用 `am start --eu android.intent.extra.STREAM <content-uri>`
   模拟分享时，应用拿得到 URI 但 `query`/`openFileDescriptor` 全部失败 → 落成
   「无法确定文件大小（file-时间戳）」的永久失败。原因是真实发送方会把 URI 放进 **`ClipData`**
   （`ShareCompat.IntentBuilder` 就是这么做的）并由系统据此授权；只塞 `EXTRA_STREAM` 的模拟没有授权。
   这既解释了那次失败，也说明解析必须同时读 `ClipData`（已实现并有去重单测）。
2. **同一批 URI 会同时出现在 `EXTRA_STREAM` 与 `ClipData`，而且两边可能是同一张照片的两种 URI 形态**：
   最初按 URI 字符串去重（`LinkedHashSet`）**不够**——真机复现出「分享一张图、上传两份」，
   详见下面第 9 条与「同一张照片被传两遍」小结。
3. **不要用 `savedInstanceState == null` 判断「是不是新的分享投递」**：分享 Intent 会成为任务的
   基础 Intent，任务带着保存状态重建该判断为假，结果是**用户分享过来什么都没发生**。
   实测踩过（用 `am start -n <pkg>/<activity>` + 计数验证时被误判过一次）。
4. **`EXTRA_STREAM` 里可能是 `String` / `String[]`**（老应用、部分 ROM）。按 `Uri` 读会在遍历元素时抛
   `ClassCastException`——分享一下就把应用崩掉，所以按宽容策略先读规范形态、失败再读字符串形态。
5. **`file://` 来源要自己取文件名**：`ContentResolver.query` 对 `file://` 返回 null，
   不补 `lastPathSegment` 就只能显示「file-时间戳」。
6. **上传全部串行**（`uploadQueue` 互斥锁）：多选五个文件时并发会把局域网带宽切成五份并堆五条通知。
7. **验收脚本自身的坑**：`select ... limit 5` 让计数永远卡在 5，于是「分享后数量没涨」被误判成
   「分享被吞了」，还基于这个假象改错了一版代码。**计数要用无 limit 的聚合查询**。
8. **`am` 的坑**：本地 shell 的 `*/*` 会被 glob 展开成路径（要整条命令加单引号）；
   `am task move-to-front` 在本机 ROM 上不存在，无法用命令行模拟「从最近任务回到应用」。
9. **用户实测报障「分享了一张图片，上传了两份」**（2026-09-30 修复）：手机端两条传输记录的源 URI 是
   `content://media/external/images/media/1000102703`（`EXTRA_STREAM`）与
   `content://media/external/file/1000102703`（`ClipData`）——**同一个媒体条目的两种 URI 形态**，
   字符串不相等，第 2 条那种字符串去重必然漏。定性依据：`created_at` 只差 123 ms（与「基础 Intent
   重复投递」那种要重启进程的路径对不上），且两条记录同名、同尺寸、同 sha256。
10. **`--grant-prefix-uri-permission` 对 MediaProvider 不生效**：本想用一条命令让两种形态都可读
    （`-d content://media/external/ --grant-prefix-uri-permission` 配 `--esa EXTRA_STREAM <两种形态>`），
    实测应用依然读不到（落成「无法确定文件大小（file-时间戳）」）。根因是 `--esa` 是**纯字符串数组**，
    系统不会为它建 `ClipData`，那条路根本没有授权。能自足使用的只有
    `-d <uri> --grant-read-uri-permission`（单 URI，冷启动同样有效）。
    排查时差点被带偏：紧跟在一次真实分享之后的测试之所以「两种形态都能读」，用的是**上一次真实分享
    遗留的临时授权**——进程一被杀就没了，`am force-stop` 后重跑立刻暴露。
11. **`am` 只有 `--esa`（String[]），没有 Uri 数组 extra**：命令行造不出「两种形态各带真实授权」的输入，
    所以这一项的最终确认必须由真实相册分享完成。
12. **「DocumentsUI 不向无障碍树暴露文件名」的旧前提是错的**（本会话修正）：vivo 的
    `com.android.documentsui/.picker.PickActivity` 列表把文件名写成普通 `TextView` 的 `text`，
    **可以按文件名定位节点点击，无需盲点**——旧结论应该出自相册式媒体选择器（那类选择器确实不暴露）。
    隐私纪律相应细化：选择器列表里同样可见用户的私有文件名（准考证、私人文档等），
    **只允许按自己的测试文件名做精确匹配点击**，绝不按坐标盲点、绝不点击非本测试创建的条目。
13. **该选择器的多选手势是「长按进入选择模式 → 点选其余项 → 点工具栏『选择』确认」**：
    **单击一个文件 = 直接返回它**（单选路径，选择器立即关闭）；溢出菜单里只有「排序方式/全选」，
    **没有「打开/完成」键，工具栏那个「选择」按钮就是确认键**（vivo 定制文案）。
    长按进入选择模式后标题会显示「已选择 N 项」，可用它核对选择数再确认。
14. **vivo 的 Toast 既不进无障碍 dump 也不进 logcat**，机器无法验证 Toast 是否弹出及文案——
    只能请用户目视确认并如实记录「用户确认」。「代码里有 Toast」不等于「真机弹了」，
    这类项的验收记录必须写明证据来源。
15. **输入法弹起会把底部输入栏顶高约 1000px**（发送按钮 y≈2533 → y≈1496），
    靠上次 dump 的坐标点「发送」会点空（消息留在草稿框）。**凡涉及底部按钮的点击，
    前面若动过输入框，一律重新 dump 取新坐标。**

#### 同一张照片被传两遍（已修）

**症状**：分享一张图片，服务端落库两条同名、同尺寸、同 sha256 的消息，`created_at` 相差 123 ms；
手机端两条传输记录的源 URI 分别是 `…/images/media/1000102703`（`EXTRA_STREAM`）与
`…/file/1000102703`（`ClipData`）。

**为什么两种形态是同一个文件**（不是猜测）：MediaProvider 里 `images`/`video`/`audio` 都是 `files` 表
之上的**视图**——`CREATE VIEW images AS SELECT … FROM files WHERE media_type=1`（AOSP
`platform_packages_providers_MediaProvider` / `DatabaseHelper.java`，Android 14）。因此同一卷内
「行 id」唯一标识一个文件，形态里的集合名只是过滤条件。设备侧核对：两种形态查出的
`_id` / `_display_name` / `_size` 完全一致。

**修法**（`android/.../share/ShareInbox.kt` 的 `mediaIdentityOf` + `dedupeUris`）：去重按条目身份，
只认已核实是 `files` 表或其视图的形态（`…/file/<id>`、`…/downloads/<id>`、
`…/images|video|audio/media/<id>`），身份取 `<卷>:<id>`。三条保守规则：

- 不在白名单的形态不合并。反例很实在：`…/images/thumbnails/<id>` 是**独立**的表，id 与 `files` 无关，
  只按「最后一段数字」合并会把缩略图和别的文件并成一个。
- 带 `?` / `#` 的不合并（`?width=` / `?height=` 会改变实际内容）。
- 其余一律退回字符串比较：**宁可重复上传，也不误合并**——重复上传看得见、忍得住，
  合并错会让用户静默少收到一个文件。

**验收**：

| 输入 | 修复前 | 修复后 |
| --- | --- | --- |
| 一个 `SEND` intent 内含同一张照片的两种形态 | ❌ 2 条上传（`seq 83`/`84`，43417 B、sha256 相同） | ✅ 1 条上传（`seq 86`，逐字节一致） |
| 同上但两个形态都拿不到读授权 | — | ✅ 仍只产生 1 行传输记录（去重发生在读取之前，与授权无关） |
| **真实相册分享（端到端确认）** | ❌ 2 条上传（`seq 80`/`81`，用户报障那次） | ✅ 1 条上传（`seq 87`，sha256 与先前完全一致） |

单测 11 → 18 项（`ShareIntentTest`：真实 URI 对、不同卷、带查询串、缩略图表、SAF 文档 URI）。
端到端确认由**真实相册分享**完成（`seq 87`）——命令行造不出「两种形态各带真实授权」的输入（见踩坑 10、11）。

**修复（2026-09-30 晚，无界面中转 Activity）**：新增 `share/ShareTrampolineActivity`，
SEND/SEND_MULTIPLE 的 intent-filter 从 MainActivity **整体**挪到它身上。中转解析分享 → 投进程级
`ShareInbox` → 以**不带分享数据**的普通启动 Intent 拉起 MainActivity → 立即 finish。三条设计纪律：

- 分享内容**只走收件箱**：转发 Intent 即使在冷启动时被系统存成任务基础 Intent，重放也解析不出分享；
  MainActivity 不再解析自身 Intent（`publishShare` / `onNewIntent` 解析路径整体移除），
  连旧版本遗留的基础 Intent 都无法再触发重复。
- 中转自身的短命任务要瞬生瞬灭：`taskAffinity=""` + `excludeFromRecents` + `noHistory` +
  `Theme.NoDisplay`（onCreate 里必须立即 finish）。
- **URI 读授权必须随路转移**：`ACTION_SEND` 授予的读权限归接收它的 Activity 所有，Activity 销毁即吊销——
  中转拿到授权直接 finish，MainActivity 就再也读不到源文件。修法是把 URI 原样装进转发 Intent 的
  `ClipData` 并带 `FLAG_GRANT_READ_URI_PERMISSION`，系统在中转仍持有授权的前提下重新授予目标
  Activity；授权寿命仍是「本进程存续期」，与改造前语义一致。

**验收（vivo V2301A / Android 14，逻辑密度 3.5，预览盒 240×260 dp = 840×1024 px）：**
全程不截图、不整屏 dump——证据来自三处可机读的落点：应用缓存里的缩略图成品、

| 正在下载时不重复取原图 | 单测覆盖（`ThumbnailSourceTest`），未单独做真机 A/B |

踩坑：

12. **`BitmapFactory` 不认 EXIF 方向**：手机竖拍照片的方向写在 EXIF 里，`BitmapFactory` 直接解码得到
    **躺倒**的图（本次的测试图 2000×1500 + `Orientation=6` 就是这情形，正确显示应为 768×1024）。
    改用 `ImageDecoder`（API 28+，minSdk 33 已覆盖）后自动摆正。顺带两条：`decoder.allocator`
    必须设 `ALLOCATOR_SOFTWARE`（硬件位图不能作为缩放源的像素读取），解码后要立刻缩到目标长边
    再进缓存——否则缓存里躺着一张 4000×3000（48 MB 堆）的原图。
13. **降采样判据要用「长边」而不是「两条边都不小于目标」**：后者把 16:9 的图当方图处理，
    短边要 800 px → 2560×1440 一点不降地整张解进内存（14 MB），而 1280×720 已经够清楚。
14. **预览尺寸不要交给 `ContentScale.Fit`**：Fit 只负责把画面缩放着画进布局盒子，布局仍占满约束——
    竖图会被塞进一个横向多出空白的大框里，气泡看着就是「图没对齐」。自己算布局尺寸
    （`fitInside`，并保证小图不放大）才贴合图像本身。
15. **「下载完成后再看预览」不能只看缓存有没有变**：缓存键跟着 `fileId` 走，从服务端取与从本机副本取
    存的**是同一张**，肉眼与时间戳都分不出来。要证明「改读了本机副本」，得让服务端那条路**真的不可用**
    （把服务端文件移走）再清缓存重启——这次就是这么做的，重建结果与先前逐字节相同。
16. **别顺手用 SQLite 命令行去读服务端数据库**：数据根里真正的库是 `lan-drop.sqlite`（WAL 模式，
    还有 `-wal`/`-shm` 两个同伴文件）。直接 `sqlite3 <目录>/lan-drop.db` 会**新建一个 0 字节的空库**
    并掩住真正的库，本次就这么误建了一个（已删）。要读就先按「库 + wal + shm 一起拷到别处再打开」
    的老规矩来。

单测：Android 86 → **89 项**（新增 `protocol/LinkTextTest`，其中一项用 15 条边界表与事实源逐条对齐）；
TS 侧从 0 起 **26 项**（`packages/protocol` 15 项链接规则、`apps/web` 11 项上传状态机）。

踩坑：

17. **「暂停」不要做成掐断在飞的请求**。第一反应是用 `AbortController` 立刻断掉当前分片，
    但那样服务端可能刚写了一半：残字节留在临时文件里、`receivedBytes` 却没推进，状态机就被推进
    「服务端认为收到了、客户端以为没发」的模糊地带（服务端有 `truncateTo` 兜底，但那是容错、
    不是常规路径）。改成在**分片之间**检查暂停标志，界面显示「暂停中…」直到当前 4 MiB 落地——
    局域网上一片是毫秒级，用户感知不到差别，换来的是状态永远不含糊。
18. **续传锚点必须每次开工都向服务端要**，不能信本地记的 `offset`：分片写进去了而响应在回程丢失时，
    本地会落后于服务端，从本地 offset 继续发就是一次必然的 409。这条不变量靠单测钉住——
    把 `job.offset = status.receivedBytes` 一行删掉，「继续时不信任本地 offset」与
    「失败后重试从服务端锚点接着传」两项立刻变红（实测）。
19. **队列只挑 `queued` 的任务**，暂停的任务不占队列：否则用户挂起一个大文件，等于把排在后面的
    小文件也一起按停。代价是 `#runJob` 返回时必须保证任务已离开 `running`/`pausing`
    （否则队列会反复挑中同一个任务空转），所以收尾处有一个兜底的 `#settle`。
20. **没有「不前进」计数器的续传循环就是一个安静的死循环**：会话在服务端被中止（例如另一个标签页
    点了取消）后，追加会一直回 409/原地不动，客户端若无脑重试就永远转下去。连续 3 片不前进即判失败，
    并给出可读原因；用户点「重试」时会重新校准锚点、必要时重建会话，所以这条失败路径是能自救的。
21. **Web 端的 `<a href>` 必须自己判协议**：`kind` 由发送方自填、服务端只校验它在白名单里，
    于是 `javascript:` 也能当 `link` 发出去。旧代码直接 `href={message.text}`——把判定收进协议包
    （`isLinkText`）之后，两端都只认 http/https，Android 侧也顺带避免了把伪协议交给 `ACTION_VIEW`。
22. **Android 发送纯 URL 一直是 `kind=text`**：`LanDropApi.sendText` 的 `kind` 默认值是 `"text"`，
    而 Web 端早就会把纯 URL 标成 `link`。结果是「同一个链接，PC 发的在手机上可点、手机发的在 PC 上
    是纯文本」。修法是把判定提到协议包里，两端共用同一条规则，而不是各自内联一个正则。
23. **`LinkInteractionListener` 是 `androidx.compose.ui.text` 下的顶层接口**，不在 `LinkAnnotation`
    里面（我按直觉写了 `LinkAnnotation.LinkInteractionListener`，编译报 Unresolved reference）。
    另外自定义监听器一旦提供就**取代**默认的 `UriHandler`，所以要自己 `runCatching` 住
    「没有应用能打开这个链接」的情况，否则用户看到的是崩溃。
24. **浏览器自动化里的文件选择器会卡住整个 CLI 会话**：`page.click()` 触发 file chooser 后，
    CLI 的模态状态不会被 `waitForEvent('filechooser') + setFiles()` 清掉，之后 `snapshot`/`reload`
    全部报 `does not handle the modal state`，只能关掉浏览器重开。正解是绕开选择器：
    `page.setInputFiles('input[type=file]', path)` 对隐藏 input 同样有效，一次 `run-code` 里
    就能把「上传 → 暂停 → 等 8 秒 → 继续 → 取消」全做完（也顺便避免了多条命令之间的时间抖动）。

踩坑：

25. **清理只发生在「启动时」和「定时器」，而服务端重启必然导致客户端断线**——所以
    启动那一轮清理的广播没有任何在线客户端能收到，客户端本地残留全靠重连后的
    `purgedUpto` 水位补齐。推论：**水位补齐不是锦上添花，而是主路径之一**；漏了它，
    「重启服务端 + 保留策略」的组合下客户端缓存永远落后。也正因为在线广播无法靠
    重启触发（等一小时定时器不现实），清理间隔做成了 env——验证时 15 秒一轮。
26. **删除按 seq 前缀而不是按 `created_at` 逐行删**：客户端只听得懂「删到 seq X 为止」。
    按 created_at 删在 `createdAt` 被显式乱序传入时会产生「中间挖洞」的删除集合，
    两端就再也对不上；前缀语义最多「多留几条较老的消息」，永不误删。
27. **上传 PATCH 必须带 `?offset=` 查询参数**（验证脚本踩的）：不带会 `409 offset_mismatch`。
    这是断点续传协议的既有约定（客户端声明本片起始位置），写脚本时容易忘。
28. **`purgedUpto` 水位持久化在 `meta` 表，不随表内容现算**：纯前缀删除下「现算」
    （`min(seq)-1`）结果碰巧一致，但**手动清空会话（`DELETE FROM messages`）会让现算
    水位瞬间归零**——「服务端历史上删过什么」这件事的信息全在表里，表一空就丢了。
    水位是独立的历史事实，落 `meta` 且只进不退（`max(旧值, 本次uptoSeq)`），
    客户端的补删才不依赖「表长什么样」。
29. **（P4-2 收尾修复）Activity 持有的 URI 授权随 Activity 销毁吊销**：把 SEND 的 intent-filter 挪进
    无界面中转后，中转拿到授权就 finish——不转移授权，MainActivity 的全体文件分享直接失效
    （表现为「无法确定文件大小」）。转移走系统标准机制：URI 装进转发 Intent 的 `ClipData` 带
    `FLAG_GRANT_READ_URI_PERMISSION`，由系统重新授予目标 Activity。另外，「任务基础 Intent 已经干净」
    直接读 `dumpsys activity recents` 里任务的 `intent={...}` 行即可证明，不必真的复现
    「杀进程 → 最近任务重开」才知道有没有修掉。

**踩坑记录**

1. **`resource_dir()` 裸跑不可靠**：target/release 直接运行时它把路径解析成了盘符根 `C:`，
   node 收到的主脚本参数变成 `C:server\server.js`（报 `EISDIR … lstat 'C:'`）。改用
   `current_exe()` 同级布局——裸跑与安装后布局一致，永远确定。
2. **sidecar 运行时按「exe 同级扁平名」解析**：`shell.sidecar()` 内部走 `exe_dir/<program>.exe`；
   externalBin 配置里的 `binaries/node` 只是打包器的**源路径**。传配置路径会找
   `exe_dir/binaries/node.exe`（os error 3）。
3. **安装目录与默认数据根撞目录**：见上表数据目录行。这个坑在「一切正常」的冒烟里看不出来，
   是对照「卸载会删什么」推出来的。
4. **rustup 镜像**：rsproxy 的 rustup dist 镜像缺 channel 清单（`/rustup/dist/channel-rust-stable.toml`
   404），rustup 换 TUNA；crates.io sparse 索引 rsproxy 正常。Windows 侧 cargo 配置写在
   `C:\Users\illag\.cargo\config.toml`。
5. **`@tauri-apps/cli` 2.12 平台包是 `.node` 原生插件**（`cli.win32-x64-msvc.node`），没有独立
   exe：Windows 侧 `npm install --registry=https://registry.npmmirror.com @tauri-apps/cli@2`，
   用本机 node 跑 `tauri.js`。
6. **构建树必须放 Windows 本地盘**：从 Windows 侧按 `\\wsl.localhost` 路径构建，9P I/O 会让 cargo
   慢到不可用；把 src-tauri 源码复制到本地盘构建（现 `E:\ClaudeCode\lan-drop-desktop-build`，
   `build.cmd` 以 `%~dp0` 相对定位，换目录零改动），产物拷回仓库。
7. **Linux 的 resources 落点与 Windows 不同**：Tauri 2 在 Linux（AppImage/deb 的 AppRun 布局）把
   resources 放 exe 的 `../lib/<productName>/`（`usr/lib/LAN-Drop/`），sidecar externalBin 却仍在
   exe 同级（`usr/bin/`）——`current_exe().parent()` 找 server.js 必须**双候选探测**（Windows 候选
   1 命中、Linux 候选 2 命中），单一路径在另一平台必踩 os error 3。
8. **`tar --strip-components` 的层数**：`node-v<ver>/linux-x64` 包里 `bin/node` 路径共 3 层，剥
   **2** 层落盘为 `./node`；剥 3 层会把文件名本身剥空，tar **静默跳过该成员**（不报错、exit 0），
   表现为「提取成功但文件不存在」。
9. **WSLg 无系统托盘**：没有 StatusNotifierWatcher，libappindicator 初始化只有 deprecation
   warning、进程不受影响，但托盘图标无处显示。壳对托盘构建失败做了降级（仅 Linux：无托盘继续
   跑，服务端常驻优先；退出交由 sidecar 意外退出路径或 `pkill -x LAN-Drop`）。托盘目视项只能
   在真 Linux 桌面验证。

### 安全加固轮（2026-10-01，改进审计后的 P0/P1 清账）

> 全面改进审计定级出三个 P0 与若干 P1，本轮逐项落地。冒烟以「失败先行」写入 5 节新
> 用例（13 项红），随后每个修复提交逐节转绿，最终 `pnpm verify` 93 项全绿。

1. **0 字节文件上传（P0）**：`POST /uploads {size:0}` → complete 曾在 `sha256File` 的
   ENOENT 上炸成 500（空文件没有任何分片请求，临时文件从未落盘）。修法：会话创建即
   `writeEmptyFile(tempPath)`；complete 增加盘上尺寸核对（`size_mismatch_on_disk`），
   把「received_bytes 与磁盘长度静默漂移」拦在入库前。Android 侧 `resolvePickedFile`
   的 `-1` 哨兵（大小未知）与 0（真空文件）此前被 `<= 0` 混为一谈，已拆开。
2. **token 泄漏面（P0）**：Android WS 握手、Web `<img>`/`<a download>` 都把 token 放
   URL，Fastify 默认访问日志原样落盘（实测确认）。修法：req 序列化器把 `token=` 值
   打码成 `[REDACTED]`（保留参数名便于排查）；`createAuthHook` 增加 `allowQueryToken`
   选项——查询凭据只对文件下载与 WS 握手放行（浏览器硬约束），其余接口一律请求头；
   Android WS 与下载全部改走 `Authorization` 头。verify-all 冒烟后扫描服务端日志，
   发现未脱敏 token 即失败。
3. **分片并发双写（P0）**：两个并发同 offset PATCH 双双读到同一个 `received_bytes`
   并各自追加（实测 receivedBytes 冲到两倍、内容交错）。修法：`Set<uploadId>` 写入
   互斥（检查与占用之间无 await），竞态回 409 `chunk_write_in_progress` 带权威进度。
4. **客户端完整性自证（P1）**：此前没有任何客户端声明 sha256，服务端校验形同虚设。
   complete 接受可选 `body.sha256`（不符 422 且中止会话）；Android 选**选项 B**——
   边传边算、收尾必带（`digest.update` 只吃服务端确认的字节，409 realign 时覆盖区间
   对齐，续传会话重读 `0..offset` 补前缀）；Web 刻意不声明（浏览器二次读盘的 UX 代价
   大于收益），不对称已记录在案。
5. **设备撤销（P1）**：token 永不过期 + 共享房间模型意味着一次配对 = 永久全权，此前
   唯一「撤销」是手工改库。现在：`DELETE /pair/devices/:id`（鉴权 + 仅回环）、回收该
   设备 open 会话与临时分片（`uploads.device_id` 无外键必须手动清）、删设备行、
   `Hub.kickDevice` 以 4401 踢下线（Android 进 `CREDENTIALS_INVALID`）；Web 控制台
   新增「设备管理」面板（`GET /pair/devices` 此前无人使用）。消息保留（sender_name
   反范式）。
6. **CI（P1）**：`.github/workflows/ci.yml` 三 job——`ts`（pnpm verify 全链路门禁）、
   `android`（JVM 单测，首跑修正两处后转正为硬门禁：v3 setup-android 安装已下架的
   tools 包必挂→删除该步骤；阿里云镜像对海外 runner 偶发超时→CI 环境官方源优先）、
   `hygiene`（ps1 BOM + 文档相对
   链接检查，`scripts/check-doc-links.mjs`）。明确不做：真机、NSIS、AppImage。
7. **`pnpm verify`（验证基建）**：`scripts/verify-all.mjs` 自起服务端（8899/8898、
   一次性临时数据根，绝不碰 8787/8788）跑全量冒烟，typecheck → 单测 → 冒烟 → 日志
   扫描一路门禁。
8. **README 威胁模型成文（P1）**：明文 HTTP / 可信局域网前提 / 配对码约 30 bit 熵、
   10 分钟、一次性、仅回环可读 / 共享房间模型 / token 可撤销但不过期 / `?token=` 是
   浏览器约束下的已知残留（会进浏览器历史与下载记录）/ 非私有网段 403。另修
   README 开发环境一节的 C:/E: 构建树矛盾。
